### Summary

Pion DTLS does not distinguish sessions created by a client from sessions created by a server. When an application shares a SessionStore between its outbound connections and its listener, a malicious server previously contacted by the application can reuse the outbound session to bypass the listener's authentication requirements. This doesn't affect webrtc users.

Discovered by Anthropic's OSS Scanner `ANT-2026-ALO2G36N`

### Details

The attacker must have completed an outbound connection initiated by the application, retain that connection's session secret, and be able to reach the application's listener. No credentials accepted by the listener are required.

During DTLS 1.2 resumption, the listener looks up the peer-supplied session ID and accepts the returned session without checking which role created it. Client sessions are stored under a key derived from the remote address and server name. The malicious server can use that key to select the client's cached session and complete the handshake using the master secret it already knows.

### Impact

The listener then accepts application data without running its normal PSK callback or client-certificate authentication checks. For example, a server trusted only for an outbound connection can gain access to a listener that requires a different PSK or a client certificate.

Pion DTLS saves resumable sessions before the original handshake has completed client authentication. An unauthenticated attacker can create an unfinished session and then resume it to bypass required client-certificate authentication. This doesn't affect webrtc users.

Pion DTLS could repeatedly process a client's certificate flight while waiting for the client's Finished message.

### Summary

Pion DTLS did not limit the size of RSA public keys in peer certificates before performing signature verification. A remote peer could provide a certificate containing an unusually large RSA modulus and trigger expensive cryptographic operations, causing excessive CPU consumption.

Discovered by Anthropic's OSS Scanner, tracking ID `3X1BUF5Y`.
### Details

The vulnerable implementation parsed peer certificates and passed their RSA public keys directly to handshake signature verification without checking the modulus size.

An attacker does not need to generate a corresponding RSA private key or provide a valid handshake signature. A certificate containing a large, attacker-chosen public modulus and an invalid signature is sufficient to trigger expensive verification before rejection.
The affected paths include verification of ServerKeyExchange and CertificateVerify. Peer certificate chains also lacked an explicit RSA key-size limit.

### Impact

Repeated or concurrent malicious handshakes can consume substantial CPU resources, reducing service availability and delaying legitimate connections.
WebRTC applications can be affected when an attacker can reach the DTLS handshake and cause an RSA verification path to execute. Using a local ECDSA certificate does not itself prevent the peer from presenting an RSA certificate.

Pion DTLS retained handshake messages in an append-only cache without a limit on entry count or total memory consumption. The cache continued accepting entries after handshake completion.

The handshake cache copied and retained each submitted message without deduplicating entries or enforcing a memory budget. Cached messages remained allocated for the lifetime of the connection.

The vulnerable implementation selected the signature verification primitive from the certificate's public key type, while deriving the digest from the peer-controlled handshake signature scheme.

### Impact

An attacker who can redirect the victim's DTLS handshake, and also have access to the peer's public certificate, may impersonate that peer without its private key.
